# Driving Detection - From Scratch CNN Multiclass Object Detector

A dashcam object detector built from scratch in PyTorch. A single shared CNN backbone with two heads (box regression + 5-class classification) trained end-to-end on real dashcam imagery. Used Resnet backbone with pretrained weights and random init as well, for a model comparison study on how much pretraining helps. Several core pieces were also implemented from scratch rather than using high-level api calls. The raw implementations are visible in the notebook, for anyone who wants to see and understand how these can be built by hand.

Every architectural and preprocessing choice below is implemented and explained step by step in the notebook. If you want to read the project, the best sarting point is the notebook, after going through this readme file.

## Problem & approach

Detect and classify 5 categories of road objects — `biker`, `car`, `pedestrian`, `truck`, `trafficLight` in dashcam footage, using one CNN trained by hand. The notebook builds every stage of this pipeline in order: data cleaning → class rebalancing → augmentation → a grid-based detection head → two loss variants (IoU vs EIoU) compared across a pretrained vs randomly-initialized backbone (Model A vs Model B) → evaluation → a real time inference demo.

## Why PyTorch and not TensorFlow

Using PyTorch was a delibrate choice I made for thir project. Reasons are,

- PyTorch has native CUDA support on Windows, whereas TensorFlow dropped native Windows GPU support from version 2.11 onwards (2.10 was the last version to support it directly). The option left is WSL2 or a Docker based setup to get CUDA working with tf on Windows. I tried setting up an NVIDIA NGC container on WSL2 (which by itself is a harder task), and the gains were minimal compared to a plain CPU run. With PyTorch, no such issues were faced running on GPU.
- Another reason is, unlike TensorFlow, PyTorch is not a high level API. This low level abstraction means I had to specifically design how the data flows through the model during training, how gradients get computed, testing on a validation set after each epoch — all of this had to be manually wired up, which gave me a lot of control over the training process, and helped me learn a lot instead of just calling .fit() and .predict().

## How to run

1. Download the dataset and deduplicate it and place them in the `clean/` folder
2. Open `Capstone_Driving_Object_Detection.ipynb` and **run it start to finish, in order**. Later sections depend on artifacts written to disk by earlier ones (eg - class remapping, duplicate-box merging, the train/valid/test split under `final_dataset/`, etc.). Running cells in random order or skipping sections will break downstream cells.
3. Training itself does not happen inside the notebook and the reason is explained in below.
4. Once you have checkpoints in `capstone_python_files/checkpoints/`, after finishing running the notebook from top to bottom, run the Flask demo.

## Built From Scratch

A number of core piecesof this notebook were deliberately implemented by hand, using raw tensor operations using NumPy and torch.tensor rather than high level library calls. Every implementation is done with vectorization in mind, instead of using raw loops to account for the speed as well. This is done as a learning exercise, to actually understand what's happening under the hood instead of trusting an api:

- Image geometric augmentation (scaling, translation, padding) with matching box coordinate remapping
- Pairwise box overlap (IoU) computation
- Duplicate bounding box merging, using a union-find algorithm
- Detection grid target encoding and decoding
- Non-max suppression
- Box regression losses (IoU and EIoU based)
- Focal loss for objectness
- Class imbalance weighting

## Model architecture

- **Backbone**: `torchvision.models.resnet18`, truncated after `layer3` (dropped `layer4`/`avgpool`/`fc`) to keep output shape `(1, 256, 26, 26)` at stride 16, matching the detection grid size (26x26) exactly.
- **Detection grid**: the image is encoded into a fixed **`(26, 26, 4, 10)`** target tensor - 26×26 cells, up to **4 independent box slots per cell** (handles multiple overlapping objects landing in the same cell), and each slot holds 10 values: objectness + `(cx, cy, w, h)` (cell-relative center, whole-image-relative size) + 5 one-hot class scores, so for each image the output tensor takes the shape of `(26, 26, 4, 10)`.
- **Two heads, one backbone**: a box-regression head and a 5 way classification head both read off the same shared backbone features, trained jointly, end to end.
- **Model A vs Model B**: identical architecture, compared with (A) an ImageNet-pretrained backbone vs (B) the same backbone but with fully randomly initialized weights, thereby isolating how much pretraining actually helps on this dataset.
- **IoU vs EIoU**: two box-regression loss variants trained and compared for each of the above, giving 4 total trained configurations.
- Thus, got a `2x2` ablation: {Model_A_IoU, Model_A_EIoU}, {Model_B_IoU, Model_B_EIoU}

## Training

As mentioned above, training was not run from inside the notebook. Setting num_workers>0 on the PyTorch DataLoader made data loading unreliable inside a Jupyter kernel on Windows — Windows spawns each worker as a fresh process that re-imports the script's **main**, and a Jupyter kernel has no real **main** for that to work against, so it broke; a plain .py file does.

So the training loop was extracted into `capstone_python_files/train.py` and run from a real terminal instead. To reproduce the 4 trained checkpoints, run this following from the terminal. You can choose which model and loss you want. Also you can adjust the epochs if needed.

```bash
python capstone_python_files/train.py --model_name modelA_iou   --pretrained    --loss iou   --epochs 30
python capstone_python_files/train.py --model_name modelA_eiou  --pretrained    --loss eiou  --epochs 30
python capstone_python_files/train.py --model_name modelB_iou   --no-pretrained --loss iou   --epochs 30
python capstone_python_files/train.py --model_name modelB_eiou  --no-pretrained --loss eiou  --epochs 30
```

Argument reference from `train.py`:

| flag                               | meaning                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------- |
| `--model_name`                     | required — name used for the checkpoint file, e.g. `modelA_iou`           |
| `--pretrained` / `--no-pretrained` | whether the ResNet18 backbone starts from ImageNet weights or random init |
| `--loss`                           | `iou` or `eiou` — which box-regression loss to train with                 |
| `--epochs`                         | number of epochs (default 30, all 4 real runs used 30)                    |
| `--lr`                             | learning rate (default `1e-4`)                                            |

## Results

Real evaluation on the held-out **test set (1,373 images)**, comparing all 4 trained models:

| model          | precision | recall | f1         |
| -------------- | --------- | ------ | ---------- |
| **modelA_iou** | 0.6117    | 0.5740 | **0.5923** |
| modelA_eiou    | 0.5954    | 0.5727 | 0.5838     |
| modelB_iou     | 0.5778    | 0.4705 | 0.5187     |
| modelB_eiou    | 0.4994    | 0.5038 | 0.5016     |

`modelA_iou` (pretrained backbone, IoU loss) is the best-performing configuration — pretraining consistently beats random init (Model A > Model B for both loss types), and plain IoU loss slightly edges out EIoU here. But since, we are dealing with multi-class detection, per-class breakdown will be the best approach in evaluating the models performance. See the notebook, for a detailed per-class breakdown for all 4 runs.

## Known limitations

- **Class imbalance**: `biker` and `truck` detection quality is real but noticeably weaker than `car`/`trafficLight`, which is a direct consequence of how imbalanced the raw dataset is, even after class collapsing and weighting.
- **Up to 4 boxes per grid cell**: objects beyond the 4th in any single 26×26 cell are dropped by design — a deliberate capacity/complexity tradeoff, not an oversight. Coule have been reduced to 3 or even 2, to see if that has any impact on the performance on crowded images.
- **CPU vs GPU inference speed**: the Flask demo's FPS depends heavily on whether it's running on a CUDA GPU or CPU-only. So expect a noticeably slower, less real time smooth playback on CPU-only hosting. But if its a GPU, it will running with ~30FPS real time.
